# Spec Documents Rules

Documents about a single GitHub issue are kept together under `docs/spec/issue<number>/`.

## Layout

```
docs/spec/
└── issue<number>/
    ├── requirements.md   # Requirements analysis (in use)
    ├── plan.md           # Plan made at the time of the work (planned)
    └── result.md         # Summary of what was actually implemented (planned)
```

- One folder per issue. The folder is created by the skill that writes the first document.
- Not every issue has every document. If a document does not exist, skip it; do not create it by hand.

---

## Documents

| File | Role | Status | Generated by |
|------|------|--------|--------------|
| `requirements.md` | Requirements analysis: what is needed, collected from the issue body, comments, and parent issue | In use | `create-gh-issue-analysis-report` |
| `plan.md` | The plan made at the time of the work: design and tasks | Planned | `create-plans` |
| `result.md` | What was actually implemented, compared to the plan | Planned (no skill yet) | N/A |

### `requirements.md`
- Describes **what** is needed, not how to implement it.
- **Read it before implementing an issue** when it exists. Agreed details often exist only in issue comments, and this document collects them.

### `plan.md`
- Describes **how** the work was planned at that time.
- Not guaranteed to match the final code. Treat `result.md` and the code as the source of truth for what was built.

### `result.md`
- Records what was implemented, including differences from `plan.md`.

---

## Change History

Every document keeps a `Change History` table (date, change, source) at the bottom.

- The document always represents the **current state**. Edit in place; do not append a new section or regenerate it.
- Add one row per update. Never rewrite past rows.
- Do not delete a dropped item or reuse its ID. Mark it as dropped with the reason.
