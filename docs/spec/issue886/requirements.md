## 배경 및 문제
현재 이슈 → PR 흐름(요구사항 분석 → 계획 → 구현 → 리뷰 → 검증 → PR)은 수동으로 진행된다. 단계마다 새 세션을 열고, 이전 산출물을 에이전트에게 알려 주고, 다음 지시를 내려야 한다. 단계별 스킬(`create-gh-issue-analysis-report`, `create-plans`, `test-driven-development`, `requesting-code-review`, `verification-before-completion`, `create-pr`)은 이미 있으나 이를 연결하는 것이 없다.

Claude Code의 동적 워크플로우는 서브에이전트를 루프·병렬로 오케스트레이션할 수 있지만, 실행 중 사용자에게 질문할 수 없다(실행 중 사용자 입력 불가). 따라서 사람의 검토 게이트는 워크플로우 안에 둘 수 없다.

## 목표
`.agents/skills/issue-to-pr` 스킬을 추가하여, 단일 호출(`/issue-to-pr <issue-number>`)로 전체 흐름을 실행한다. 사람의 검토 게이트는 메인 세션에서 처리하고, 장시간 실행 구간은 동적 워크플로우에 위임한다. 최종 검증은 사람이 Draft PR에서 수행한다.

## 범위
### 포함
- `.agents/skills/issue-to-pr` 스킬 신규 추가
- 동적 워크플로우 `plan-to-pr` 추가 (게이트 2 통과 후의 무인 구간 담당)
- 흐름 전체: 사전 질문 → 요구사항 분석 → 게이트 1 → 계획 수립 → 게이트 2 → 동적 워크플로우(구현 → 자체 테스트 → 코드 리뷰/토론 → 최종 검증 → Draft PR)
- 자체 테스트 정책 및 토론 라운드 상한 처리

### 제외
- 스킬을 `nlab-agent`(`platforms/claude/`)로 승격 (skaengus2012/nlab-agent#26에서 추적)
- `create-pr`의 범용 버전 승격 (프로세스 골격은 공유 저장소, 브랜치/커밋 규칙은 각 프로젝트 가이드라인)

## 기능 요구사항
| ID | 요구사항 | 출처 |
|----|----------|------|
| FR-1 | `/issue-to-pr <issue-number>` 단일 호출로 전체 흐름을 실행한다. | 본문 (스킬 이름은 사용자 변경, 변경 이력 참고) |
| FR-2 | 시작 전 항상 다음을 질문한다: 시작 지점(`requirements.md` / `plan.md`가 있으면 이어서 진행), 코드 리뷰 토론 최대 라운드 수, Draft PR 생성 여부, 리뷰어 모델. | 본문 (Flow 1) |
| FR-3 | 요구사항 분석을 서브에이전트가 `create-gh-issue-analysis-report`로 수행한다. | 본문 (Flow 2) |
| FR-4 | 게이트 1: 메인 세션에서 사람이 요구사항을 검토한다(승인 / 수정 요청). 승인될 때까지 반복한다. | 본문 (Flow 3) |
| FR-5 | 계획 수립을 서브에이전트가 `create-plans`로 수행하며, 테스트 전략(단위 테스트만 / 단위 테스트 + 자동 UI QA)을 포함한다. | 본문 (Flow 4) |
| FR-6 | 게이트 2: 메인 세션에서 사람이 계획을 검토한다(승인 / 수정 요청). 승인될 때까지 반복한다. | 본문 (Flow 5) |
| FR-7 | 동적 워크플로우(사용자 입력 불필요)가 구현(TDD) → 자체 테스트 → 코드 리뷰 → 최종 검증 → Draft PR 순으로 수행한다. | 본문 (Flow 6) |
| FR-8 | 코드 리뷰는 구현자와 별개의 리뷰어 에이전트가 수행하며, 구현자와 제한된 횟수의 피드백 토론을 한다. | 본문 (Flow 6) |
| FR-9 | Draft PR은 기존 `create-pr` 스킬로 생성한다. | 본문 (Flow 6) |
| FR-10 | 자체 테스트 기본값은 변경된 모듈로 범위를 한정한 단위 테스트이다. | 본문 (자체 테스트 정책) |
| FR-11 | UI 변경 시 계획의 테스트 전략에 따라 자동 UI QA(Maestro)를 고려한다. | 본문 (자체 테스트 정책) |
| FR-12 | 디바이스/에뮬레이터가 없으면 UI QA를 건너뛰고 PR 본문에 "manual UI check required"를 기록한다. | 본문 (자체 테스트 정책) |
| FR-13 | 토론 라운드는 상한을 두며, 해결되지 않은 쟁점은 PR 본문에 기록한다. | 본문 (설계 제약) |
| FR-14 | 요구사항이 모호하면 추측하지 않고 실행을 멈춘 뒤 질문으로 보고한다. | 본문 (설계 제약) |
| FR-15 | 서브에이전트에는 스킬 매칭에 의존하는 것에 더해 명시적 파일 경로(예: "`.agents/skills/create-pr/SKILL.md`를 읽을 것")를 전달한다. | 본문 (설계 제약) |

## 영향 범위
코드 확인 결과:
- `.agents/skills/` 하위에 현재 `create-jacoco-report-and-show`, `create-mockup`, `create-pr`, `git-worktree-creator`가 있으며, `issue-to-pr`는 여기에 추가된다.
- `.agents/workflows/`, `.claude/workflows/` 디렉터리는 현재 존재하지 않는다.
- `docs/guidelines/spec-docs.md`가 `docs/spec/issue<number>/` 구조(`requirements.md`, `plan.md`, `mockup/`)를 정의하며, 스킬의 spec 디렉터리 설정이 이를 따른다.
- 연계 대상 기존 스킬: `create-gh-issue-analysis-report`, `create-plans`, `test-driven-development`, `requesting-code-review`, `verification-before-completion`, `create-pr`.

## 미해결 질문
- 워크플로우 규모: 설계를 현재 가이드라인(에이전트 5개 미만)에 맞출지, "Dynamic workflow size"를 상향할지 결정이 필요하다. (본문에서 구현 중 확인할 항목으로 명시됨)
- 사전 질문 답변을 JSON 객체로 워크플로우 `args`에 전달하는 방식이 동작하는지 구현 중 검증이 필요하다. (본문에서 확인 필요 항목으로 명시됨)
- 워크플로우 `plan-to-pr`의 저장 위치(스크립트 파일 경로)가 정해져 있지 않다. `.agents/workflows/`와 `.claude/workflows/`는 현재 존재하지 않는다.
- 리뷰어 모델 선택지의 범위(어떤 모델을 제시할지)와 기본값이 명시되어 있지 않다.
- "토론 라운드 최대 횟수"의 기본값이 명시되어 있지 않다.
- 계획 단계의 테스트 전략에서 자동 UI QA 적용 여부를 판단하는 기준(어떤 변경이 UI 변경인지)이 명시되어 있지 않다.
- 최종 검증 단계에서 실패 시(테스트 실패 등) 워크플로우의 동작(중단 / 재시도 / Draft PR 생성 여부)이 명시되어 있지 않다.
- 사전 질문에서 "Draft PR 생성 안 함"을 선택한 경우 워크플로우의 종료 지점과 산출물이 명시되어 있지 않다.

## 충돌 및 참고
- 댓글과 상위 이슈가 없으므로 본문 내 충돌은 없다.
- 이름 변경: 이슈 본문은 원래 스킬 `start_issue`와 `start_` 접두사 이름 규칙을 명시했으나, 사용자가 접두사 불필요 및 스킬 `issue-to-pr`, 워크플로우 `plan-to-pr`로 변경하고 이슈 제목과 본문에도 반영했다(2026-11-01T15:27:34Z). 현재 본문과 이 문서는 일치한다.
- 스킬과 워크플로우의 역할 구분: 스킬 `issue-to-pr`가 진입점이며 사전 질문, 요구사항 분석, 게이트 1·2, 계획 수립을 메인 세션에서 처리한다. 워크플로우 `plan-to-pr`는 게이트 2 통과 후의 무인 구간(구현 → 자체 테스트 → 리뷰/토론 → 최종 검증 → Draft PR)만 담당한다.
- 본문의 "스파이크 결과"(Claude Code 2.1.316에서 읽기 전용 워크플로우로 검증)는 요구사항이 아니라 설계 근거이다: 저장된 워크플로우의 `args`가 전역 `args`로 전달됨, `model: 'opus'` 옵션 동작, 워크플로우 서브에이전트가 프로젝트 스킬의 `SKILL.md`를 읽을 수 있음, MCP 도구(Maestro `list_devices`) 사용 가능, `pipeline` 팬아웃의 병렬 실행.
